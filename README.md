# Shopping List

Home assignment: a two-screen shopping list application.

1. **Shopping list**: pick a category and a product, set a quantity, add to the cart. The cart is grouped by category.
2. **Order**: enter full name, full address and email (all required), review the selected products and confirm. The order is sent to the Node server and stored in Elasticsearch.

## Architecture

| Folder | Stack | Role |
|---|---|---|
| `client/` | React 19, TypeScript, Redux Toolkit (RTK Query), Vite | UI, Hebrew / RTL |
| `server-catalog/` | .NET 10, Entity Framework Core (Code First), SQL Server | `GET /api/categories`: categories with their products |
| `server-orders/` | Node.js, Express 5, TypeScript, zod, Elasticsearch | `POST /api/orders`: validates and stores an order |

The three parts are independent processes that talk to each other only over HTTP. The browser calls both servers directly (CORS is enabled for the client origins).

## Quick start (Docker)

Requirements: Docker with Compose, about 4 GB of free memory (Elasticsearch and SQL Server).

```
docker compose up --build
```

The first start takes a few minutes. When everything is up:

| What | URL |
|---|---|
| Client | http://localhost:3000 |
| Catalog API | http://localhost:5249/api/categories |
| Swagger UI (catalog) | http://localhost:5249/swagger |
| Orders API health | http://localhost:4000/health |
| Elasticsearch | http://localhost:9200 |

The catalog database is created and seeded automatically on start (EF Core migrations). The Elasticsearch `orders` index is created on start from `server-orders/mapping.json`.

To check that an order was stored:

```
curl http://localhost:9200/orders/_search
```

To stop and remove everything, including the data volumes:

```
docker compose down -v
```

## Running a service without Docker (optional)

Start the databases with `docker compose up -d sqlserver elasticsearch`, then:

- **Catalog:** in `server-catalog/` store the connection string in User Secrets and run:
  ```
  dotnet user-secrets set "ConnectionStrings:Catalog" "Server=localhost,1433;Database=CatalogDb;User Id=sa;Password=myStrong!Passw0rd;TrustServerCertificate=True"
  dotnet run
  ```
- **Orders:** in `server-orders/` run `npm ci` and `npm run dev` (port 4000, Elasticsearch at `http://localhost:9200`).
- **Client:** in `client/` run `npm ci` and `npm run dev` (http://localhost:5173).

## API contract

- `GET /api/categories` → `200` `[{ id, name, products: [{ id, name }] }]`, sorted by name.
- `POST /api/orders` with `{ customer: { fullName, address, email }, items: [{ productId, productName, categoryId, categoryName, quantity }] }`
  - `201` `{ orderId }`
  - `400` `{ errors: [{ field, message }] }`
  - `500` `{ message }`
- Validation: `fullName` ≤ 100, `address` ≤ 200, `email` valid and ≤ 254, `quantity` 1–99, `items` not empty with unique `productId`. The client validates for convenience, the server validates for safety.

## Design decisions

- **Order = snapshot.** Product and category names are stored inside the order, so it stays readable if the catalog changes and the Node server does not depend on SQL Server.
- **Elasticsearch mapping** (`server-orders/mapping.json`): `dynamic: strict` (unknown fields are rejected), `items` is `nested`, `email` is `keyword`, no replicas on a single node. `orderId` is a UUID generated by the server and used as the document id.
- **Catalog query** projects straight into DTOs (`AsNoTracking`, `Select`) instead of `Include`: one SQL query, no circular references.
- **Cart** is merged by `productId`; quantities are summed and capped at 99.

## Limitations (deliberate, for a demo)

- Passwords are plain literals in `docker-compose.yml` so the project runs without any setup. In production they come from a secret store.
- Elasticsearch runs with security disabled (`xpack.security.enabled=false`). In production enable TLS and authentication.
- EF migrations are applied at API startup (`Database.Migrate()`). This is fine for one instance; in production migrations run as a separate deployment step.
- The catalog API runs with `ASPNETCORE_ENVIRONMENT=Development` in compose so that Swagger UI is available.
- API addresses are baked into the client at build time (`VITE_CATALOG_URL`, `VITE_ORDERS_URL`, defaults `http://localhost:5249` and `http://localhost:4000`).
- No authentication and no automated tests.
